# Agent-first PDF review: feasible approaches

Research for [Identify feasible agent-first PDF review approaches](https://github.com/rickono/cookbook-mcp/issues/3), checked 2026-09-13. This is a capability comparison and proposed feasibility path, not an engine selection or approval policy. No inference, OCR, rendering, downloads, installations, paid requests, or book-data transfers were performed.

**Finding:** an agent can coordinate the existing bounded tools, but that alone does not let it verify their transcription against the pixels. Reducing human review to edge cases requires a visual reviewer whose accuracy and abstention behavior are measured. Neither a local model's resource fit nor any visual model's cookbook accuracy is established here.

## Existing boundary and integration points

The launcher admits one network-disabled job, capped at 2 GiB memory with no swap, two CPUs, 64 processes/threads, and five minutes, inside a Linux VM capped at 4 GiB. Native execution and automatic remote fallback are refused. These ceilings remain fixed; any future local visual-model trial must use the same launcher and separately prepared dependencies. [Resource isolation, exact project revision](https://github.com/rickono/cookbook-mcp/blob/d7516c9c2ae4816c4193cbf8d4f7f0c2c508dc3c/docs/ocr-resource-isolation.md).

The project already binds source/page identity, images and recognition configuration to a result digest. A correction replaces the page transcription; `decide` is documented as explicit human action. The publication gate checks review records and indexed text. There is no agent-review authority or actor identity in this decision record. An agent pass should therefore produce a separate proposal until the owner settles authority. This is an integration inference from [OCR records and decisions](https://github.com/rickono/cookbook-mcp/blob/d7516c9c2ae4816c4193cbf8d4f7f0c2c508dc3c/src/cookbook/ocr.py#L249) and [publication checks](https://github.com/rickono/cookbook-mcp/blob/d7516c9c2ae4816c4193cbf8d4f7f0c2c508dc3c/src/cookbook/quality.py#L32).

## Small comparison

| Approach | What it can inspect and do | Data location and feasibility |
| --- | --- | --- |
| Agent coordinates existing native-text/OCR candidates | Choose bounded regional retries, compare quantities, and prepare proposals from tool results. Tesseract exposes word boxes and confidence through TSV. A text-only reviewer cannot independently read the source pixels. | OCR remains local. A hosted orchestrating model still receives any candidate text returned to it; local tools do not imply local model processing. A fully local language-model orchestrator would also need a separate fit check. This path helps triage but does not establish source-grounded visual review. [Tesseract TSV](https://tesseract-ocr.github.io/tessdoc/Command-Line-Usage.html#tsv-output), [application-side function execution and returned tool output](https://developers.openai.com/api/docs/guides/function-calling#the-tool-calling-flow). |
| Local multimodal reviewer beside the bounded OCR workflow | A runtime such as llama.cpp supports image input with a compatible language model and multimodal projector. It could compare a region and candidate text in an isolated batch job. | Book content can remain local with pre-staged files and network disabled. Runtime support is documented; a suitable model's peak memory, CPU latency, fraction accuracy, and abstention are **unverified** under this project's limits. Quantized weight size alone does not establish whole-job fit. No model is selected. [Pinned llama.cpp multimodal documentation](https://github.com/ggml-org/llama.cpp/blob/5f436dddb440a288ee5611d7d1eca564a6aca9f4/docs/multimodal.md). |
| External multimodal reviewer after local preparation | A vision API can accept page/region images alongside candidate text. OpenAI documents image input through URLs, encoded data, or file IDs; it also documents small-text, rotation, localization, and accuracy limitations. | Selected pixels and accompanying text leave the device. A local path or locally generated crop does not avoid this when its contents enter the request. An authorized external adapter would be a separate path, never a network exception inside the OCR job. Availability, cost, retention settings, and accuracy need evaluation. [Image inputs and limitations](https://developers.openai.com/api/docs/guides/images-vision). |

For the external example, API data is not used for training by default, but this does **not** mean no retention: abuse-monitoring logs may be retained for up to 30 days by default, and endpoint/application-state exceptions apply. Account controls and image/file exceptions must be checked before adopting that path; this note does not generalize API terms to desktop/chat products. [OpenAI API data controls](https://developers.openai.com/api/docs/guides/your-data).

## Evidence contract to evaluate

Proposed review output should reference an immutable evidence bundle: source hash, physical page, original render hash, region coordinates plus orientation/transform, candidate text hashes and engine configuration. The trial machinery already uses hashes and normalized regions, but snippet checks do not establish complete reading order or table associations. [Trial specification and limitations](https://github.com/rickono/cookbook-mcp/blob/d7516c9c2ae4816c4193cbf8d4f7f0c2c508dc3c/docs/pdf-corpus-trials.md).

Alongside that bundle, evaluate a proposal containing the exact before/after span, inspected scope, evidence references, unresolved alternatives, reviewer/model/version, and bounded attempts taken. Distinguish `proposed correction`, `no change found in inspected scope`, `unresolved`, and `review failed`; none inherently means approved. Crops need enough neighboring content to verify ingredient-to-quantity association, with full-page context available for omissions and continuation. These fields are a design proposal, not existing storage guarantees. Schema-constrained output can make records machine-readable, but does not ensure their truth. [Structured Outputs limitations](https://developers.openai.com/api/docs/guides/structured-outputs#handling-mistakes).

Two failure modes deserve explicit evaluation. First, candidate variants or repeated reviewers may share the same wrong reading; agreement is not independent evidence. Second, a fluent reviewer may substitute a plausible quantity or method while overlooking unreadable pixels, an omitted row, or a continuation page. These are risk inferences, not measured failure rates. The trial helper already treats agreement as non-acceptance, and vision documentation does not promise perfect recognition. [Candidate triage](https://github.com/rickono/cookbook-mcp/blob/d7516c9c2ae4816c4193cbf8d4f7f0c2c508dc3c/scripts/pdf_candidate_trial.py#L41), [vision limitations](https://developers.openai.com/api/docs/guides/images-vision#limitations).

## Bounded path to a decision

1. Settle whether book pixels or extracted text may reach an external reviewer. This selects which feasibility branches are admissible; it does not settle correction authority.
2. Define a frozen evaluation covering quantities, omissions, reading order, table associations, poor scans, and apparently clean pages. Measure unsupported corrections and missed errors alongside recovered content, escalation volume, latency, and cost. Sampling only flagged pages cannot reveal all missed errors. This is the proposed evaluation design, not a completed benchmark.
3. If the local branch is chosen, separately authorize dependency preparation and test a candidate within the unchanged launcher limits. Record peak whole-job memory and completion/failure. If it cannot fit, retain that finding rather than raising the ceiling or switching processing location automatically. If the external branch is chosen, settle the allowed evidence bundle, account controls, and spending cap before a bounded trial.
4. Use those results to choose the reviewer and stopping/escalation rules. Approval authority and publication eligibility remain owner decisions; no confidence score or repeated agreement resolves them here.

Sharp questions now available: **What content may leave the device? What evaluation evidence demonstrates acceptable unsupported-correction and missed-error rates? What attempt budget turns an unsuccessful recovery into a human edge case?** These depend respectively on owner data-handling preferences, the evaluation design, and measured reviewer behavior. The longer-term fraction-recognition and throughput questions should follow those answers.
