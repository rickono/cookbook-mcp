## Existing identity and client contracts

**Source/test evidence — resource authorization.** `JWTVerifier.verify_token` checks RS256 signatures, exact issuer and audience, required time/identity claims, expiry/not-before, and an explicit subject allowlist. MCP configuration requires `library:read`; readiness separately requires that scope. The general verifier returns the authorized-party claim as client identity but does not apply the publisher's client-ID equality check. Therefore a new reader client needs a valid user-delegated library token for the existing allowed subject, not merely successful Google authentication. An ID token is not the API access credential. [Verifier and MCP configuration](../src/cookbook/server.py), [authorization assertions](../tests/test_library_auth.py), [Auth0 access-token validation](https://auth0.com/docs/secure/tokens/access-tokens/validate-access-tokens).

**Source/test evidence — transport is not a browser session.** MCP is stateless HTTP with JSON responses and bearer authorization. The application supplies allowed Host/Origin values for the configured resource origin; no reader login/callback/logout routes, cookie-to-bearer adapter or explicit application CORS middleware appear in `create_app`. This does not establish the pinned SDK's complete CORS behavior. A different-origin reader requires verification of SDK/proxy behavior and deliberate admission, rather than assuming the existing Origin guard grants CORS. Same-origin hosting avoids cross-origin API fetches but still needs a reader and authentication integration. [Application construction](../src/cookbook/server.py), [pinned dependency](../pyproject.toml), [browser CORS behavior](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS).

**Source/test evidence — publisher is native.** The process opens an external browser, binds a fixed IPv4 loopback callback before login, uses S256 PKCE plus random state and checks callback host/path and response issuer. It exchanges the code over HTTPS without redirects or a client secret, rejects any refresh token, then validates the signed token and exact client/scope. The token stays in process memory and its accessor rejects expiry. There is no renewal or application logout flow. Synthetic tests assert rejection of mismatched state/issuer/host, claims, redirects and unexpected refresh tokens. [Implementation](../src/cookbook/publisher_login.py), [test assertions](../tests/test_publisher_login.py).

**Documented support and inference — loopback cannot supply away-from-Mac reader login.** Native loopback redirects target the device running the native listener. On a phone/tablet, loopback is that device, not the Mac. A hosted browser page supplies no native listener. The publisher registration/flow must not be treated as a hosted-reader callback or a portable sign-in session. The existing identity provider and API can be reused while selecting an appropriate web-client contract. [Native OAuth, sections 7.3 and 8](https://www.rfc-editor.org/rfc/rfc8252.html), [Auth0 PKCE](https://auth0.com/docs/get-started/authentication-and-authorization-flow/authorization-code-flow-with-pkce).

**Source/test evidence — local dashboard, inspected read-only in the parent checkout.** Its uncommitted `docs/dashboard.md`, `src/cookbook/dashboard/cli.py` (`main`), `remote.py` (`_collect`) and `web.py` (`local_only`) establish a loopback-only metadata observer. `--remote-login` invokes the publisher flow and passes a bearer accessor to the local server; tokens are not sent to dashboard JavaScript. Expiry requires restarting and signing in again. The optional collector calls only publication metadata and catalog search. The web layer rejects nonlocal clients/hosts and foreign Origins and sets no-store and restrictive CSP headers. `tests/test_dashboard.py::test_filters_escaping_and_local_http_boundary` contains corresponding boundary assertions. These parent-checkout sources are **not present in this report branch**, have no immutable GitHub source link yet, and were neither modified nor copied. This is provisional evidence to recheck against the eventual dashboard commit; it proves no deployed dashboard login or phone access.

## Supported hosted options and their prerequisites

### A. Hosted same-origin application with server-managed sessions

**Documented support.** A Regular Web Application performs the code exchange using confidential client authentication. A backend can keep API tokens server-side and associate them with an application session. A reader frontend then calls its same-origin backend with a session cookie; the backend calls the shared library machinery or protected MCP using the user's API token. Keeping tokens exclusively in a server-side store with only an opaque session identifier in the cookie is an available design, not a fact about today's implementation. [Auth0 code flow](https://auth0.com/docs/get-started/authentication-and-authorization-flow/authorization-code-flow), [Auth0 token storage](https://auth0.com/docs/secure/security-guidance/data-security/token-storage).

**Prerequisites/inference.** Provide hosted HTTPS login/callback/logout and content routes, confidential credentials held only by the backend, exact callback/logout registration, the existing identity connection and least-privilege library grant, and explicit per-session authorization. Decide how sessions/tokens survive restart or multiple server instances; memory-only storage loses them on process loss. If colocated with the library, preserve the same identity and access checks rather than making content public behind a UI-only gate. These are implementation requirements derived from the option, not existing configured capabilities. [Existing bearer boundary](../src/cookbook/server.py), [Auth0 code flow](https://auth0.com/docs/get-started/authentication-and-authorization-flow/authorization-code-flow).

### B. Hosted public browser client with Authorization Code + PKCE

**Documented support.** Auth0's SPA SDK uses Universal Login and code flow with PKCE. Browser JavaScript is a public client and must not contain a client secret. Tokens can remain in browser memory; Auth0 recommends that over persistent browser storage. Memory does not survive refresh or supply a shared cache across tabs; local storage persists but exposes tokens to successful script injection. PKCE protects the code exchange, not all effects of hostile application JavaScript. [Auth0 PKCE](https://auth0.com/docs/get-started/authentication-and-authorization-flow/authorization-code-flow-with-pkce), [token storage](https://auth0.com/docs/secure/security-guidance/data-security/token-storage), [SPA SDK](https://auth0.com/docs/libraries/auth0-single-page-app-sdk).

**Prerequisites/inference.** Provide an appropriate SPA registration, HTTPS reader origin, callback handling, existing identity connection and user-delegated API access. Browser requests need the library access-token audience and read scope. Same-origin reader/API delivery reduces API CORS requirements but does not remove OAuth registration or browser token custody. A separate origin additionally needs the API's Origin admission and CORS preflight/response policy for Authorization and required MCP headers/methods. Auth0 Allowed Web Origins and Allowed Origins (CORS) govern Auth0 interactions, not the library server. [Application settings](https://auth0.com/docs/get-started/applications/application-settings), [existing transport guard](../src/cookbook/server.py), [CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS).

## Security and lifecycle constraints for either option

- **Callback integrity:** use exact registered redirects, no open redirectors, transaction-bound PKCE and correlation/state; validate issuer and OIDC nonce when relevant. Public clients must use PKCE; it is recommended for confidential clients. A hosted HTTPS callback is a different contract from a native loopback exception. [OAuth Security BCP, sections 2.1 and 4.7](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.1).
- **Renewal:** application-session expiry, API-token expiry, Auth0 SSO and upstream Google sessions are distinct. Silent authentication can fail with login/consent requirements and browser third-party-cookie restrictions. Rotating refresh tokens avoid relying on an iframe's access to the Auth0 cookie, but require configured issuance and requested offline access. Rotation detects reuse and can invalidate the token family; failure must lead to reauthentication, not an authorization bypass. Durations remain owner choices. [Silent authentication](https://auth0.com/docs/authenticate/login/configure-silent-authentication), [rotation](https://auth0.com/docs/secure/tokens/refresh-tokens/refresh-token-rotation), [session layers](https://auth0.com/docs/authenticate/login/logout).
- **Logout:** clear the application session/token cache; separately decide whether to end Auth0 SSO and upstream identity-provider sessions. Refresh-token revocation is separate from clearing cookies. The current verifier checks JWTs locally and has no logout/revocation lookup; it cannot promise immediate invalidation of a copied still-valid access token. [Auth0 logout layers](https://auth0.com/docs/authenticate/login/logout), [refresh revocation](https://auth0.com/docs/secure/tokens/refresh-tokens/revoke-refresh-tokens), [verifier](../src/cookbook/server.py).
- **Cookies:** a server-session design needs Secure, HttpOnly, bounded scope and an explicit SameSite policy compatible with the callback method. Lax can allow top-level safe-method navigations; Strict can exclude cross-site callbacks; None requires Secure. HttpOnly prevents script reading but still attaches cookies to script-initiated requests. Cookie lifetime alone is not server-session invalidation. [Browser cookie semantics](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie).
- **CSRF:** ambient cookie authorization requires protection for session-changing and state-changing requests, including logout and any future personal reading state. Verify Origin and/or use appropriate anti-CSRF tokens; SameSite is defense in depth. OAuth transaction checks address callback CSRF, not every application endpoint. A read-only product still has authentication/session transitions. [Browser CSRF guidance](https://developer.mozilla.org/en-US/docs/Web/Security/Attacks/CSRF), [OAuth callback protections](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.7).
- **CSP/content isolation:** treat source content as untrusted data, escape or sanitize it, restrict scripts and connections, and set frame/form/base policies. CSP is an additional defense against script injection, not a replacement for safe rendering. A browser OAuth client needs specifically permitted Auth0 connections and possibly SDK worker/frame resources; a backend-session design can keep browser API calls same-origin. Existing MCP widget policy or the local dashboard CSP does not establish a suitable hosted-reader policy. [Browser CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP), [existing widget declarations](../src/cookbook/server.py).
